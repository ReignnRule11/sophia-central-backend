# Permanent Sophis Central Institution ID policy

## Format

Student and lecturer accounts receive one permanent, catalogue-backed public identifier at account creation:

`SC-[TYPE]-[INSTITUTION CODE]-[ROLE]-[RANDOM]`

Examples (illustrative):
- `SC-UNI-UNILAG-STU-7K4M9Q2D8X`
- `SC-POL-YABATECH-LEC-9P3W6K8R2T`
- `SC-COE-FCEZARIA-STU-4M8K2R7W9P`

The components are:
- `SC`: Sophis Central.
- Type: fixed three-character category code (`UNI`, `POL`, `MON`, `COE`, `CHT`, `COA`, `COL`, or `OTH`).
- Institution code: catalogue-owned, uppercase alphanumeric code, 4–10 characters.
- Role: `STU` or `LEC`; reviewer access preserves the underlying student/lecturer identity.
- Random suffix: ten Crockford Base32 characters, generated server-side.

The full identifier fits the existing 32-character account identifier column.

## Institution catalogue codes

- Codes are generated by the backend when a catalogue institution is created and backfilled for existing institutions by migration.
- Recognised abbreviations are preserved where explicitly mapped (including UNILAG, YABATECH, FCEZARIA, FUTA, UNIBEN, UNIPORT, UNIZIK, LASU, UNILORIN, FUTMINNA, FUTO, FEDPONEK and other catalogue abbreviations).
- Other institutions receive a deterministic category/name-derived code with a hash suffix to reduce collisions.
- Codes are unique, not user-editable, and are not reassigned.
- Institution UUID remains the authoritative foreign-key identity. The public code is a stable human-readable catalogue reference.
- Institution category is catalogue data, not a user-entered registration value.

## Account lifecycle

- New student and lecturer registration must select an approved institution from the catalogue. The backend validates the institution UUID and generates the public ID; clients cannot supply or choose the ID.
- Existing accounts are linked only when their saved institution name exactly matches a catalogue record (case-insensitive). No fuzzy or guessed matching is performed.
- Unmatched legacy accounts keep their current ID until the account holder selects a catalogue institution in profile setup. The backend then assigns the catalogue link and generates the permanent-format ID once.
- Once assigned, the institution UUID and public Institution ID cannot be changed or cleared through profile editing. A future verified transfer/multiple-membership workflow must be designed separately.
- Institution display-name changes do not rewrite previously issued account IDs.

## Authentication, authorization and audit

- The public Institution ID can be used as a login identifier alongside email and academic handle. A password is still required.
- The Institution ID is not a password, secret, bearer token, or second factor. Knowing it alone must never grant access.
- Upload, download, and private file access continue to require an authenticated session and the existing role/resource ownership/permission checks.
- Resource upload records retain the uploader's catalogue institution reference. Activity events record the acting user's institution reference for uploads, downloads and authenticated file access.
- Downloaded-resource access remains account-scoped through the internal user UUID; the public Institution ID is not used as an authorization bypass.
- Account deletion continues to anonymize retained approved-resource contributors. Do not copy the public Institution ID into retained resource attribution.

## Deployment and reconciliation

1. Review the institution-code backfill output in a staging copy before production migration.
2. Confirm that every existing catalogue record receives a unique code and inspect the generated abbreviations, especially institutions without an established public abbreviation.
3. Apply the migration once through the normal migration workflow; do not run it as part of the daily account-deletion cron.
4. Review legacy users with null `institutionId`. Exact-name matches are linked automatically; all other users must select the correct catalogue entry before their public ID is refreshed.
5. Verify student and lecturer signup, email verification, login by email/handle/Institution ID, dashboard display/copy, upload, in-app download, and downloaded-file access.
6. Confirm upload/download/file-access activity events include the institution reference and that resource access still enforces authenticated permissions.

The migration must be tested against a production-like database snapshot before production execution. Never use a live production database for a destructive or speculative test.
